# 01. 프로젝트 계획서 (Project Plan)

- 프로젝트명: joongo_notify
- 문서 버전: v0.2 (초안)
- 작성일: 2026-07-09
- 상태: 검토 대기

### 확정된 전제 (발주자 결정, 2026-07-09)
- **개인 1인용**이다. 다중 사용자 격리는 설계하지 않는다. 단, 접속 편의를 위해 **웹 UI + 자체 인증(단일 계정) 로그인**을 Phase 1부터 두고, **카카오 OAuth 로그인**을 옵션으로 추가한다 (Watch 관리는 웹에서, 알림은 텔레그램으로).
- **수집 빈도는 낮게 유지**한다. 기본 수집 주기 30분, 필요 시 Watch별로 늘리는 방향(줄이는 방향 아님). 실시간성보다 플랫폼 부담 최소화·차단 회피가 우선.
- 자동 채팅(조건 부합 + 확실한 구매의사 시 판매자에게 상세 정보 요청)은 **목표에 포함**한다. 단, 자동 결제·구매 확정은 하지 않는다.
- 수집·자동 채팅 모두 **RPA(브라우저 자동화) 필요 가능성이 높다**고 본다. 구체 방식은 `10-collection-research.md`에서 확정.

## 1. 배경과 문제 정의

중고 거래 플랫폼(당근마켓, 중고나라, 번개장터)에서 원하는 제품을 사려면:

1. 플랫폼 3곳을 **각각** 반복 검색해야 하고,
2. 검색 결과 대부분이 원하는 모델·상태가 아니며 (모델명 표기가 제각각, 상태 정보는 본문/사진에 흩어져 있음),
3. 상태 확인(번인, 기스 등)은 **본문을 읽고 사진을 직접 봐야만** 가능하고,
4. 좋은 매물은 수 시간 내에 팔리므로 **먼저 발견하는 사람이 이긴다**.

즉, "원하는 상태의 매물을 사람이 감시하는 것"은 반복적이고 시간에 민감한 작업이며, 자동화 가치가 크다.

## 2. 목표

> 사용자가 **제품 + 상태 조건 + 지역/가격**을 등록하면, 시스템이 3개 플랫폼을 감시하여
> 조건에 맞는 매물을 **본문·사진까지 분석한 뒤** 점수를 매겨 알림으로 보내준다.

### 목표에 포함되는 것
- 관심 상품(Watch) 등록: 제품, 상태 조건, 지역(당근마켓), 가격 범위
- 3개 플랫폼 매물 수집 및 통합 스키마 정규화
- 3단계 분석 파이프라인: 검색엔진 필터 → 경량 로컬 LLM 본문 분석 → VL 모델 사진 검증
- 매칭 점수 산출 및 임계값 초과 시 알림 (텔레그램 우선)
- 카테고리/제품/상태속성 온톨로지 정의 (전자제품부터)
- 자동 채팅 — 상세한 가격대와 확실한 구매의사가 있는 매물에 한해, 판매자에게 빠른 채팅·상세 정보 요청 (Phase 3, → FR-D6)
- 판매자 신뢰도 평가 (후속 단계 후보)

### 목표에서 제외되는 것 (Non-goals)

- 자동 결제·구매 확정 (문의까지만 자동화, 거래 결정은 사람이)
- 다중 사용자 서비스 (개인 1인용 확정 — 위 전제 참조)
- 시세 예측 (후속 단계 후보 — 수집 데이터가 쌓이면 자연스럽게 가능)

### 3.1 계층별 설명

| 계층 | 역할 | 핵심 설계 포인트 |
|---|---|---|
| **수집기 (Collector)** | 플랫폼별 어댑터가 신규 매물을 주기 수집 | 플랫폼별 접근 방식이 전부 다름(§5). 어댑터 인터페이스로 추상화. 레이트리밋·백오프 필수 |
| **정규화 (Normalizer)** | 플랫폼별 필드를 통합 `Listing` 스키마로 변환, 중복 제거 | 동일 매물이 여러 플랫폼에 올라오는 경우 탐지(제목+가격+이미지 해시 유사도) |
| **① 검색엔진 필터** | 모델명·별칭·키워드로 후보 압축 | 전체 매물의 95%+를 여기서 저비용 탈락. 제품 별칭 사전이 품질 좌우 ("아이폰14프로" = "iP14P" = "아이폰 14 pro") |
| **② 경량 LLM 분석** | 본문 텍스트 → 구조화된 상태 속성(JSON) 추출 | 한국어 성능 좋은 소형 모델. 카테고리별 속성 스키마를 프롬프트에 주입. "언급 없음"을 명시적 값으로 처리 |
| **③ VL 사진 검증** | 사진에서 상태 조건 검증 (번인/기스/파손) | 비용이 크므로 ①②를 통과한 매물만. 판정은 확정이 아닌 **신뢰도 점수** (사진으로 번인 판별은 본질적으로 불확실) |
| **매칭/스코어링** | 사용자 조건 vs 분석 결과 → 0~100점 | 필수 조건(hard) / 선호 조건(soft) 구분. 정보 없음 ≠ 조건 위반 (감점만) |
| **알림** | 임계값 초과 매물 즉시 발송 | 텔레그램 봇 우선(구축 최저비용). 매물 링크·사진·분석 요약·점수 포함 |

### 3.2 데이터 모델 핵심 개념

- **Category**: 계층형 카테고리 (전자제품 > 모니터/스마트폰/노트북 …). 카테고리마다 **상태 속성 스키마**를 가짐.
- **ConditionAttribute**: 카테고리별 상태 속성. 예) 스마트폰: `번인(없음/약함/심함)`, `외관기스(S/A/B/C)`, `배터리효율(%)`, `침수이력(bool)`, `구성품(리스트)`, `보증잔여(개월)`.
- **Product**: 제품 카탈로그 항목. 정식 모델명 + **별칭 리스트**(검색엔진 필터의 재료) + 소속 카테고리.
- **Watch**: 사용자의 감시 등록. Product + 조건값(필수/선호) + 지역 + 가격범위 + 알림 채널.
- **Listing**: 정규화된 매물. 원본 플랫폼, URL, 제목, 본문, 가격, 지역, 이미지들, 게시시각.
- **AnalysisReport**: 매물 1건에 대한 분석 결과. 속성별 (값, 근거 텍스트/이미지, 신뢰도, 출처=본문|사진).
- **MatchResult**: Watch × Listing 매칭 점수와 속성별 판정 내역 (알림 본문의 재료).

## 4. 기술 선택 (초안 — 프로토타입에서 검증 후 확정)

| 영역 | 1순위 후보 | 근거 / 대안 |
|---|---|---|
| 언어/런타임 | Python 3.12 | 크롤링·ML 생태계. 대안: 수집기만 Node |
| 검색엔진(①필터) | Phase 1: 자체 별칭 매처 (정규화 문자열 매칭, 인프로세스) → 규모 확대 시 Meilisearch | ①단계의 실체는 "별칭 사전 매칭"이므로 MVP에 외부 검색엔진은 과함. 별칭 사전 품질이 관건 |
| 경량 로컬 LLM | 벤치마크 시점의 SOTA 경량 모델을 조사해 2~3종 후보 선정 (후보 예: Qwythos-9B 등, 한국어 성능 필수) | 모델 세대교체가 빠르므로 문서에 특정 모델을 못박지 않음. `11-model-benchmark.md`에서 후보 확정·측정. NFR-1 하드웨어에서 양자화 구동 가능해야 함 |
| VL 모델 | Qwen2.5-VL 3B/7B | 경량 VL 중 성능 우수. 대안: InternVL2 계열. GPU 없으면 7B는 무리 → 3B 양자화 우선 검증 |
| 서빙 | Ollama (LLM+VL 겸용) | 단일 서버로 운영 단순화 |
| DB | PostgreSQL (프로토타입은 SQLite) | Listing/Report 이력 축적 |
| 큐/스케줄러 | 초기: APScheduler + DB 큐 → 규모 커지면 Redis+Celery | 초기 규모에 과한 인프라 배제 |
| 수집 | httpx + Playwright(필요 플랫폼만) | §5 조사 결과에 따라 플랫폼별 결정 |
| 알림 | 텔레그램 Bot API | 무료·즉시·양방향. 카카오 알림톡은 사업자 등록 필요라 제외 |
| UI / 인증 | Phase 1: 경량 웹 UI (FastAPI + 서버사이드 템플릿) + **자체 인증**(단일 계정 ID/PW, 세션 쿠키) → P1 옵션: **카카오 OAuth**(카카오 디벨로퍼스 개인 앱으로 무료 사용 가능) | Watch 등록·관리는 웹에서. UI는 최소한으로 시작해 Phase 3에서 고도화 |

## 5. 플랫폼별 수집 전략과 리스크 ⚠️

**이 프로젝트의 최대 리스크는 AI가 아니라 수집이다.** 3사 모두 공식 오픈 API가 없고, 약관상 자동 수집을 제한한다. Phase 0에서 반드시 다음을 조사·문서화한다 (→ 문서 `10-collection-research.md`).

**RPA(브라우저 자동화) 필요 가능성이 높다.** 단순 HTTP 수집이 막히는 플랫폼은 Playwright 기반 RPA로 접근하고, 자동 채팅(FR-D6)은 본인 계정 로그인 세션이 필요하므로 RPA가 사실상 유일한 경로다. 로그인 세션 유지(persistent context)·차단 감지 방식을 10번 문서에서 플랫폼별로 확정한다. 개인용·저빈도 운영이 이 접근의 전제 조건이다.

| 플랫폼 | 특성 | 예상 접근 방식 | 리스크 |
|---|---|---|---|
| 당근마켓 | **지역 기반** — 지역 설정 없이는 검색 불가. 웹 검색 페이지 존재 | 웹 검색 엔드포인트 + 지역 파라미터 | 지역 인증, 봇 차단, 웹 노출 매물이 앱 대비 부분집합일 가능성 |
| 번개장터 | 웹 서비스 충실, 내부 JSON API 구조가 비교적 관찰 용이 | 웹 내부 API 관찰 기반 수집 | 비공식 API 변경에 취약 → 어댑터 계층에서 격리 |
| 중고나라 | 자체 앱/웹 + **네이버 카페**의 이중 생태계 | 자체 웹 우선, 카페는 검색 노출 경로 조사 | 카페 글은 비정형 텍스트 → LLM 분석 의존도 최대 |

**공통 원칙 (필수 준수):**
- robots.txt 및 약관 검토 결과를 문서로 남기고, 금지가 명확한 경로는 사용하지 않는다.
- 개인 사용 수준의 낮은 요청 빈도: 기본 수집 주기 30분, 플랫폼당 분당 수 회 이하, User-Agent 명시, 지수 백오프. 실시간성을 위해 빈도를 올리는 튜닝은 하지 않는다 (확정 전제).
- 수집 데이터는 개인 매칭 용도로만 저장하고 재배포하지 않는다. 판매자 개인정보(닉네임·프로필)는 최소 수집.
- 차단·구조 변경을 상시 가정: 어댑터별 헬스체크와 "수집 실패" 알림을 1급 기능으로 취급 (기능 요구서 FR-D4).

## 6. 분석 파이프라인 상세 설계 방향

### 3단계 깔때기(funnel) — 비용 관리가 핵심
```
일일 신규 매물 (플랫폼당 수천 건, 키워드 사전 필터 후 수백 건)
  → ① 검색엔진: 모델 별칭 매칭          [수 ms/건]  → 후보 ~수십 건
  → ② 경량 LLM: 본문 → 속성 JSON       [~수 초/건]  → 조건 근접 매물 ~수 건
  → ③ VL: 조건 관련 사진 검증           [~수십 초/건] → 최종 판정
```
②에서 확정 탈락(예: "번인 있음" 명시, 필수 조건 위반)이면 ③을 건너뛴다. ③은 "본문에 언급 없음 + 사진 존재 + 해당 조건이 시각 검증 가능"일 때만 실행.

### 정확도에 대한 현실적 스탠스
- VL로 사진 속 번인·기스를 판별하는 것은 **불확실성이 크다** (조명, 촬영 각도, 저해상도).
- 따라서 시스템의 판정은 "확정"이 아니라 **신뢰도 딸린 소견**이며, 알림 메시지에 근거(해당 문장, 해당 사진)를 함께 보여 사용자가 최종 판단하게 한다.
- 오탐(잘못 알림)보다 **미탐(놓침)이 더 나쁘다**: 경계 사례는 낮은 점수로라도 알림에 포함하는 방향으로 튜닝. (좋은 매물을 놓치면 서비스 존재 이유가 사라짐)
- 평가용 골든셋(라벨링된 실매물 100~200건)을 Phase 1에서 만들어 추출 정확도를 회귀 측정한다 (→ 문서 `12-ai-eval-plan.md`).

### Phase 0 — 조사·설계 확정 (1~2주)
- [ ] 플랫폼 3사 수집 가능성 조사 및 법적/약관 검토 문서화 (`10-collection-research.md`) — RPA 필요 여부, 자동 채팅 경로·계정 리스크 포함
- [ ] 벤치마크 시점 SOTA 경량 LLM 후보 조사(2~3종) + VL 1~2종 로컬 벤치마크: 실매물 텍스트 30건·사진 30장으로 추출 품질 확인
- [ ] 카테고리/속성 온톨로지 v1: 전자제품 3개 카테고리(스마트폰·모니터·노트북)만 정의
- **완료 기준**: 기술 선택 확정, 기능 요구서 v1.0 승인

### Phase 1 — MVP: 1개 플랫폼 끝까지 (2~4주)
- [ ] 번개장터(수집 난도 최저 예상) 어댑터 + 정규화 + SQLite 저장
- [ ] 검색엔진 필터 + LLM 본문 분석 + 스코어링 (VL 제외)
- [ ] 경량 웹 UI: 자체 인증 로그인 + Watch 등록/관리 폼
- [ ] 텔레그램 알림 발송
- [ ] 평가 골든셋 구축, 추출 정확도 측정
- **완료 기준**: "아이폰 14 프로, 번인 없음, 90만원 이하" Watch를 등록하면 실제 조건 부합 매물이 텔레그램으로 온다

### Phase 2 — 3개 플랫폼 + VL (3~4주)
- [ ] 당근마켓(지역 파라미터) + 중고나라 어댑터
- [ ] 교차 플랫폼 중복 제거
- [ ] VL 사진 검증 단계 투입 + 신뢰도 표기
- [ ] PostgreSQL 전환, 어댑터 헬스체크/장애 알림
- **완료 기준**: 3개 플랫폼 동시 감시, 사진 근거가 알림에 포함

### Phase 3 — 확장 (지속)
- [ ] 자동 채팅 (FR-D6): 고점수 매물에 판매자 문의 자동 발송 — 사전 승인 모드부터, RPA 세션 기반
- [ ] 웹 UI 고도화 (매물 이력, 시세 그래프) + 카카오 OAuth (P1에서 미도입 시)
- [ ] 카테고리 확장 (가구, 악기, 유아용품 …) — 온톨로지 편집 도구
- [ ] 사용자 피드백 루프 ("이 매물 아님" 버튼 → 매칭 튜닝)

## 8. 리스크 총괄

| 리스크 | 확률 | 영향 | 대응 |
|---|---|---|---|
| 플랫폼 수집 차단/약관 문제 | 높음 | 치명 | Phase 0 선행 조사, 어댑터 격리, 저빈도 수집, 개인 사용 범위 유지 |
| 경량 LLM의 한국어 추출 품질 부족 | 중간 | 높음 | Phase 0 벤치마크로 조기 검증, 프롬프트에 few-shot 예시, 실패 시 모델 상향 |
| VL 판정 신뢰도 낮음 | 높음 | 중간 | 판정을 참고 정보로 격하, 근거 사진 첨부, 임계값 보수 운영 |
| 모델명 별칭 커버리지 부족 → 미탐 | 중간 | 높음 | 별칭 사전을 데이터로 관리, 미탐 사례 발견 시 사전 갱신 프로세스 |
| 1인 개발 범위 과다 | 높음 | 중간 | Phase 1을 "1개 플랫폼 + VL 제외"로 강하게 제한 |
| 자동 채팅으로 인한 본인 계정 제재 | 중간 | 높음 | Phase 3까지 보류, 사전 승인 모드 기본, 발송 빈도 상한, 플랫폼별 리스크를 10번 문서에서 평가 후 진행 여부 결정 |

## 9. 성공 지표 (Phase 1 기준)

- Watch 등록 → 첫 유효 알림까지 평균 소요 < 24h (매물 존재 가정)
- 신규 매물 게시 → 알림 도달 지연 < 수집 주기(기본 30분) + 5분 (저빈도 운영 전제 — 실시간성은 목표가 아님)
- 본문 속성 추출 정확도 ≥ 85% (골든셋 기준)
- 알림 정밀도(사용자가 "맞는 매물"로 판단한 비율) ≥ 70%
